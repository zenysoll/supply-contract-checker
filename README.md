# Проверка условий договоров поставки

Прототип для тестового задания Product Owner, Semantic TextNavigator (Stereos Group). Автор: Евгений Соловьев, сделано в Claude Code.

Закупщик загружает TXT-файлы (договоры, допсоглашения, письма, проекты) и видит по каждому договору номер, поставщика, сумму в рублях и срок поставки на дату проверки. У каждого значения есть файл, дословная цитата и переход к абзацу с подсветкой. Если значение изменено, видно, каким допсоглашением и что было в договоре. Письма, проекты и не вступившие допсоглашения показаны отдельной колонкой. Внутри нет LLM, сети и платных API: правила и регулярные выражения на стандартной библиотеке Python.

## Быстрый старт за 30 секунд

Нужен Python 3.9 или новее, больше ничего ставить не надо.

```bash
python3 run.py --preload sample_documents      # откроется http://127.0.0.1:8000 с 6 учебными файлами
python3 run.py --report sample_documents/*.txt # то же в консоли, без браузера
python3 -m unittest discover -s tests -t .     # 110 тестов, около секунды
```

В интерфейсе: перетащите TXT на страницу или нажмите «Загрузить TXT». «Дата проверки» вверху по умолчанию 10.03.2026, при смене таблица пересчитывается. В блоке «Вопросы» можно спросить обычным текстом, нажать готовый вопрос или включить фильтр «поставка раньше …». Клик по источнику открывает документ справа на нужном абзаце.

То же через API (сервер запущен):

```bash
curl -G localhost:8000/api/ask --data-urlencode "q=Какова сумма договора STN-102?"
curl "localhost:8000/api/early?before=2026-04-01&as_of=2026-03-10"
curl localhost:8000/api/state          # вся таблица в JSON, у каждого значения source: файл, абзац, цитата, смещения
```

Состояние в памяти, после перезапуска файлы загружаются заново. Ключей и секретов нет, сервер слушает только 127.0.0.1.

## Ответы на 4 вопроса (исходные документы, 10.03.2026)

| Вопрос | Ответ и основание |
|---|---|
| Срок по STN-101 | **30.04.2026.** Допсоглашение № 1 подписано обеими сторонами и вступило в силу 01.03.2026 (`02_amendment_signed.txt`, п. 2). В договоре было 15.04.2026. Проект ДС № 2 (10.05.2026) не подписан, показан отдельно |
| Сумма STN-102 | **840 000 ₽** (`03_contract.txt`, п. 2.1). Аванс 252 000 ₽ за сумму не принят |
| Сумма STN-103 | **Нет данных.** В п. 2.1 сказано, что стоимость определяется приложением № 1, которого в комплекте нет. Лимит 600 000 ₽ из п. 2.2 за стоимость не принят |
| Поставка раньше 01.04.2026 | **STN-102 (20.03.2026).** Есть несогласованное изменение: письмо поставщика предлагает 27.03.2026, согласия покупателя нет. У STN-101 тоже есть несогласованный проект (10.05.2026), но действующий срок 30.04 и раньше апреля не попадает |

## Как проверить, что ничего не выдумано

- Ответов в коде нет: `grep -rnE "STN|840|380|20\.03|30\.04|0[1-6]_" checker/ run.py` находит только два комментария с примерами формата. Тип и статус документа определяются по тексту, имя файла в логике не участвует (тест переименовывает файлы и перемешивает порядок).
- Каждая цитата это `text[start:end]` исходного файла. Тест `test_every_source_quote_is_exact_text_of_the_document` проверяет это для всех источников, включая отклонённые суммы и предложения.
- Значение без источника не выводится. Если числа нет, показывается «нет данных» и цитата, где это сказано. Если правило не уверено (относительный срок, сумма «увеличить на …», условное вступление в силу, две разные даты), показывается «нужна проверка», а не догадка.
- Поменяйте любое поле в копии документа и прогоните `python3 run.py --report папка/*.txt`: значение и цитата поменяются вместе с текстом.

## Как добавить новое поле (например, ставку неустойки)

Всё, что ниже извлечения (правило допсоглашений, цитаты, таблица, API, вопросы, консольный отчёт), работает по реестру `FIELDS` в `checker/extract.py`. Поэтому новое поле это одна функция и одна строка:

1. В `checker/extract.py` написать `extract_<поле>(sent) -> [Hit]`: на вход одно предложение, на выход найденные значения. `Hit("value", значение, "как показать")`, `Hit("absent", reason=...)` если прямо сказано, что значения нет, `Hit("ignored", ..., reason=...)` для похожих, но не тех чисел. Источник и смещения проставит `scan_hits`.
2. Добавить строку в `FIELDS`: ключ, подпись колонки, функция, форматтер значения, слова, по которым вопрос относится к полю.
3. Добавить тест рядом с `tests/test_field_registry.py` (там пример с игрушечным полем «аванс»): значение и цитата на исходных файлах, «нет данных», изменение допсоглашением.
4. Прогнать тесты и `python3 run.py --report sample_documents/*.txt`.

Для неустойки в учебных данных есть ловушки: в STN-103 «ставка неустойки … не установлена» (должно быть «нет данных» с цитатой), а в ДС № 1 «размер неустойки остаётся без изменений» (это не новое значение). Проценты сейчас не разбираются, понадобится маленький парсер вида «0,1% … за каждый день» в `numbers.py`.

## Записка

**Пользователь.** Специалист по закупкам: сверяет условия поставок, не перечитывая пачку документов, и должен за секунды убедиться в ответе по цитате. Юридического заключения прототип не даёт.

**Пять вопросов клиенту перед развитием**
1. Какие документы приходят на деле (скан PDF, DOCX, ЭДО, почта), сколько их и где они живут сейчас?
2. Какие поля нужны после суммы и срока: неустойка, НДС, этапы и частичные поставки, приёмка, валюта?
3. Как у вас определяется действующая редакция: бывают ли допсоглашения задним числом, с условием вступления в силу, цены в спецификациях, подписи только на сканах?
4. Кто какие договоры видит, и можно ли закупщику знать, что есть документ, к которому у него нет доступа?
5. Что дороже: пропущенное изменение или лишнее «нужна проверка»? Куда закупщик несёт ответ дальше (ERP, письмо поставщику)?

**Допущения**
- Документы похожи на учебные: заголовок с типом, строка «Статус:», пронумерованные пункты, суммы в рублях.
- Условия меняет только допсоглашение, подписанное обеими сторонами и вступившее в силу не позже даты проверки. Письмо и проект только показываются. Подписанное, но ещё не вступившее допсоглашение тоже показывается отдельно, с пометкой «ещё не действует».
- Порядок допсоглашений берётся из содержимого (дата вступления в силу, затем подписания), а не из имени файла или порядка загрузки.
- Подписание определяется по тексту статуса, сами подписи я не вижу.
- Документ относится к договору, если в нём указан номер этого договора. Ссылка на два договора делает связь неоднозначной, такой документ не применяется.
- Без уверенности лучше «нужна проверка», чем число.

**Две метрики**
1. Качество: доля значений без пометки «нужна проверка», которые закупщик подтвердил по цитате без правки, на размеченной выборке реальных договоров. Цель от 98%. Отдельно считаю «уверенно неверные» значения, цель ноль. Мерить так: правка значения в интерфейсе пишется в журнал и становится эталоном.
2. Полезность: медианное время от открытия договора до решения закупщика, до и после внедрения (замер на 20-30 типовых задачах). Цель минус 50%. Вспомогательно: доля строк с «нужна проверка», если она растёт, инструмент перестают открывать.

**Архитектура**

```
TXT -> абзацы и предложения со смещениями (textutil) -> тип, статус, даты, номер (extract)
    -> поля по реестру FIELDS (extract) -> привязка к договору по номеру (engine)
    -> состояние документа на дату проверки -> выбор значения поля (engine)
    -> JSON API на http.server (server) -> одна HTML-страница (static/index.html)
```

**Три решения и компромиссы**
1. **Правила вместо LLM.** Результат повторяемый, проверяемый, бесплатный и работает офлайн. Цена: понимает только типовые русские формулировки. Всё нераспознанное уходит в «нужна проверка», а не в догадку.
2. **Нет источника, нет значения.** Цитата это дословный фрагмент текста со смещениями, переход к абзацу работает по ним. Компромисс: цитата целым предложением, в допсоглашении она включает «Пункт 3.1 договора изложить…».
3. **Консервативное применение изменений.** Неясный статус, условная или двойная дата вступления в силу, ссылка на несколько договоров: допсоглашение не применяется, строка получает флаг. Больше флагов, зато нет неверной суммы. Ложный флаг я считаю дешевле.

**100 000 документов и права доступа.** Разбирать один раз при загрузке и хранить факты (поля, цитаты, смещения, версия правил) в БД, оригиналы в объектном хранилище. Сейчас всё пересчитывается на каждый запрос: 10 тыс. файлов около 3 с, для 100 тыс. так нельзя. Индекс «номер договора → документы», пересчёт только затронутого договора, таблица с пагинацией и серверными фильтрами, полнотекстовый поиск. Права на уровне документа и договора, фильтрация до вычисления ответа, чтобы счётчики и пометка «есть изменение» ничего не раскрывали; просмотр абзаца проходит ту же проверку, обращения пишутся в журнал. Если закупщику недоступно допсоглашение, он не должен получить уверенное «действующее значение»: нужен флаг «есть документ вне вашего доступа» (вопрос 4 клиенту).

**Три следующих улучшения по приоритету**
1. Спецификации и приложения (у STN-103 нет суммы именно поэтому), этапы поставки, относительные сроки («30 дней с оплаты»).
2. Правка значения из интерфейса с записью в эталон: это и метрика качества, и регрессионный набор для правил.
3. Новые поля через реестр (неустойка, НДС, валюта), затем PDF/DOCX, права доступа и постоянное хранилище. LLM только как подсказчик для нестандартных формулировок, с обязательной проверкой, что цитата дословно есть в тексте.

## Известные ограничения

- Только TXT. Абзац это строка, строки с жёстким переносом склеиваются по эвристике.
- Поля: сумма и срок поставки, по одному значению на договор. Несколько дат поставки в одном предложении дают «нужна проверка».
- Сумма без «руб./рублей/₽» не распознаётся («нет данных»). Другая валюта и расхождение цифр с прописью дают «нужна проверка».
- Приложения и спецификации не разбираются, загруженное приложение даёт флаг «проверьте вручную».
- Чисто числовой номер договора без слова «договор» в допсоглашении не найдётся.
- Статус берётся из строки «Статус:» или фразы «подписано обеими сторонами». Просто «подписано» без уточнения даёт «нужна проверка».
- Проверено на 6 учебных документах и синтетических копиях (в том числе 300 случайно собранных наборов), на реальных договорах не проверялось.

## Отчёт о вайбкодинге

**Инструмент:** Claude Code. Код и тесты писались им по моей постановке, я задавал рамки, читал документы сам и сверял результат со своими ответами.

**Характерные запросы**
1. «Прототип без платных API и без LLM внутри. Для каждой суммы и срока дать файл, точную цитату и переход к абзацу. Тип документа определять по содержимому, не по имени файла. Ничего не вшивать: на встрече загрузят новый договор того же формата».
2. «Сначала прочитай все документы и выпиши ответы на 4 вопроса вручную. Потом запусти приложение и сверь. Тесты на исходных файлах и на изменённых копиях: сумма, дата, статус, дата вступления в силу, отсутствующие данные».
3. «Смоделируй встречу: поменяй одно поле в копии договора, добавь новый договор с допсоглашением, прогони через консоль и через API curl-ом. Потом проверь, сколько мест в коде надо тронуть, чтобы добавить поле неустойки».

**Ошибки ИИ и как их поймал**
- Фразу «дата приемки … не изменяет срок по пункту 3.1» правило считало изменением срока: глагол ловился без учёта «не». Итоговые ответы были верными, заметил, только когда попросил вывести все срабатывания по каждому файлу. Отрицаемые слова теперь вырезаются, есть тест.
- Регулярка суммы съедала точку в конце предложения и теряла цифры в записи «1 380 000 (… рублей 00 копеек)». Нашлось на прогоне по строкам, добавлены тесты на разные записи суммы.
- Привязка документов к договорам была квадратичной, на ~2500 сгенерированных файлов прогон не завершился за 2 минуты. Переписано в один проход, 10 тыс. файлов около 3 с.
- В README первой версии было написано «новое поле = функция плюс строка в FIELDS», а на деле поле было зашито ещё в пяти местах: строка таблицы, подписи ответов, слова в вопросах, колонки страницы, консольный отчёт. Заметил, когда прошёлся по коду с вопросом «что трогать для неустойки». Сделал реестр полей по-настоящему и добавил тест, который регистрирует игрушечное поле и проверяет весь путь до ответа на вопрос. Этот же тест поймал вторую ошибку: справочник полей собирался один раз при импорте и не видел поля, добавленные позже.
- На сценарии встречи подписанное, но ещё не вступившее допсоглашение попадало в ответ под заголовком «несогласованные изменения». По сути оно согласовано, просто не действует. Заголовок теперь различает эти случаи, добавлен тест сценария встречи.

**Как проверялось.** 110 автотестов: исходные файлы и ответы на 4 вопроса; дословность всех цитат; изменённые копии (сумма и срок в разных записях, статусы, дата вступления в силу, отсутствие данных, переименование, новый договор, кодировка cp1251); HTTP-сценарий; 300 случайно собранных наборов с независимым расчётом ожидаемого результата. Чтобы убедиться, что случайные тесты что-то ловят, временно сломал правило (применять неподписанные допсоглашения): тест упал. Сценарий встречи (изменённая сумма STN-102, новый STN-104 с допсоглашением после даты проверки, смена даты проверки) прогнан через `--report` и через API curl-ом.

**Затраты времени.** Около 1,5 часа с Claude Code, включая проверку и README.

**Не успел / осталось**
- Спецификации и приложения, этапы поставки, относительные сроки.
- Поле неустойки (оставлено для встречи, путь описан выше), правка значения из интерфейса.
- Постоянное хранение, права доступа, PDF и DOCX.
- Проверка на реальных договорах и размеченном эталоне, поэтому метрики пока не измерены.
